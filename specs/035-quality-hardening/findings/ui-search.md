## Adjudication Log

- `SearchPanel.tsx:66,82-85,112-120,148,291` (stale pagination cursor across a branch switch, disputed by Pass 2): **kept**. Adjudicator traced `App.tsx` and confirmed `SearchPanel` stays mounted across a branch switch (no `key` prop, `finalizeBranchSwitch` never resets `searchPresentation` or the panel's `cursor`) and confirmed server-side `parseCursor` is a branch-agnostic offset — the stale-offset path is reachable. See SE-008.
- **SE-003 fixed (Phase 8 Checkpoint F2)**: added a comment above the `generatedLocalLabel`/`localOnly` branches in `SearchResults.tsx` explaining that the more specific `generatedLocalState`-derived label takes precedence, with the plain `localOnly` flag only used as a fallback when the server didn't report a more specific state — no logic change. Verified via `tsc --noEmit` and the full `vitest run` (444/444, including `SearchResults.test.tsx` unchanged).
- **SE-004 fixed (Phase 8 Checkpoint F3)**: added dedicated `'name-match'`/`'content-match'` icons to `MetaTagIcon`/`iconFor` in `meta-tag.tsx` (a document/page glyph, plain for name matches and with content lines for content matches) and switched `SearchResults.tsx` to use them in place of the semantically-unrelated `'git'`/`'local-change'` icons. No label/behavior change. Verified via `tsc --noEmit` and the full `vitest run`.
- **SE-001 + SE-002 + SE-006 fixed (Phase 7 Checkpoint G3)**: before consolidating, traced every `App.tsx` call site that sets the 7 committed props (`searchQuery`/`searchMode`/`searchCaseSensitive`/`searchRootPath`/`searchContentKind`/`searchTrackedMode`/`searchLimit`) to confirm the effects could be safely merged. The only place all 7 change together is the `onSearch` handler (~line 1418), which sets them atomically in one batched event handler. Every other call site that touches a subset of them (repo-path reset, ~line 365; `handleSelectSearchResult`, line 799; `handleDismissSearch`, line 851) always pairs it with `setSearchPresentation('collapsed')` in the same batch, which unmounts `SearchPanel` (it's conditionally rendered only when `searchPresentation === 'expanded'`) before the mismatched partial props could ever be observed by the draft-sync effect. So the 7 props never change independently while the panel is mounted, and consolidating their sync effects into one is behavior-preserving. Merged the 7 single-purpose `useEffect`s (SE-001) into one effect keyed on all 7 committed props that sets all 8 draft fields (including `cursor`) in a single pass — this is also what SE-002 and SE-006 describe as "unnecessary machinery," since both point at the same 7-effect fan-out as their root cause; no further change was made to the draft/committed-value split itself, since that split (local draft state distinct from the submitted values `useQuery` reads) is required by the panel's submit-to-apply UX, not by inefficiency — collapsing it further (e.g. into a `useReducer`) would be a disproportionate rewrite per CLAUDE.md's anti-overengineering guidance for a low/medium-severity efficiency finding. Verified via `tsc --noEmit` and the full `vitest run` (444/444 UI tests unchanged).
- **SE-005 deferred (Phase 7 Checkpoint G3)**: kept `verified` but not fixed. The finding's own evidence already downgrades it to a pre-existing project-wide pattern (no component in the codebase uses `React.memo`) with bounded result counts (25-100), so wrapping only `SearchResults` in `React.memo` would be a unit-local inconsistency with the rest of the codebase rather than a real fix — same self-disqualifying-evidence basis used to defer FT-004/FT-005/FT-007 and SH-001/NM-006/NM-009 earlier in this phase.
- **SE-007 fixed (Phase 7 Checkpoint G3)**: removed the dead `&& submittedMode !== undefined` clause from `readyForResults` in `SearchPanel.tsx` — `mode` is a non-optional typed prop so the check was always true. `readyForResults` is now simply `submittedQuery.length >= 3`. No behavior change. Verified via `tsc --noEmit` and the full `vitest run`.
- **SE-008 fixed (Phase 7 Checkpoint G3)**: added a dedicated `useEffect(() => { setCursor('') }, [branch])` in `SearchPanel.tsx` so pagination `cursor` resets whenever the mounted panel's branch changes, closing the gap where "Load more" could reissue a stale offset against the new branch after a branch switch. Kept separate from the SE-001 consolidation above since `branch` has no corresponding draft field to mirror — this effect exists solely to reset pagination state. Verified via `tsc --noEmit` and the full `vitest run`.

## Architecture Notes

The unit is small and its three files have clean separation: `SearchTrigger` is a trivial stateless button, `SearchResults` is a pure presentational list, and `SearchPanel` is the sole stateful piece. The main structural concern is that `SearchPanel` is a controlled component from the parent's perspective (`App.tsx` owns query/mode/caseSensitive/rootPath/contentKinds/trackedMode/limit as the committed search state) but re-implements an uncontrolled draft/form layer on top via seven props mirrored into local state plus seven single-purpose `useEffect`s plus a manual `isDraftDirty` diff — a "submit-to-apply" form pattern that would be far simpler as an internal `useReducer` or a single derived-state object, and that is the dominant complexity driver in the whole unit (SE-001, SE-002, SE-006). On the cross-cutting checks requested for this batch: `SearchResult.matchType` is used correctly and consistently as `'name' | 'content'` matching the server type (`src/types.ts`), with no divergence from Batch C's UT-001 found in this unit; and no client-side inefficiency compounds Batch A's SG-004 server-side git `ls-files` re-spawn — react-query's queryKey correctly gates refetches on actual submitted-value changes (not draft keystrokes), so this UI does not cause extra search requests beyond what the user explicitly submits or paginates.
