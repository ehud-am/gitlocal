## Adjudication Log

- `src/handlers/file.ts` 166-264 (SH-001) — **DEFERRED**: updateFileHandler and deleteFileHandler share structure (JSON parse, path parse, branch resolution, pathType check) but diverge in the order and content of operation-specific checks — update additionally validates `content` type and runs a `type !== 'markdown' && type !== 'text'` editability check that delete has no equivalent for, and each emits distinct error messages per failure. Merging them into one parameterized handler risks silently reordering which validation wins when multiple conditions fail on the same request, changing existing test-asserted error messages/precedence for edge-case payloads. Addressed the safe, provably-behavior-preserving portion instead (SH-002 payload-parsing extraction, SH-003/SH-005 branch-resolution extraction, SH-004 response-builder extraction); the remaining control-flow overlap is left as-is per spec.md US4 Scenario 2 (reject/defer rather than force a false abstraction where blocks differ in edge-case handling).
- `src/handlers/repo.ts` 164-172 — **KEPT**: Confirmed reachable and real. `path` is the raw, client-supplied string (see src/handlers/repo.ts:149-167); `resolvedInputPath` = classification.canonicalPath is produced via resolve() + realpathSync() (src/git/repo.ts:291-293,315,331), which both resolves relative segments/symlinks and normalizes case-insensitive filesystem casing. In the non-git branch, `selectedPath = basename(path)` uses the pre-canonicalization string while the git branch two lines below correctly derives selectedPath from resolvedInputPath (relative(rootPath, resolvedInputPath)) -- an inconsistency within the same function. Client paths are not guaranteed canonical: (1) ui/src/components/Picker/PickerPage.tsx:173/191 sends free-typed text (`path.trim()`) directly to /api/repo/open with no client-side canonicalization; (2) native/macos/GitLocal/GitLocal/AppDelegate.swift:46-58 forwards `url.path` from macOS LaunchServices 'Open With' events verbatim (native/macos ViewerWindowController.swift:143-158 dispatches it as-is), and Finder/LaunchServices routinely hands out symlinked or differently-cased paths on APFS/HFS+ (case-insensitive by default). Consumption is not merely cosmetic: ui/src/App.tsx uses `selectedPath` as `path` in persisted viewer state and as a react-query key for getSyncStatus/getRepoLocation (App.tsx:289-290,391,539-543), so a wrong basename can mislabel the opened file and desync UI state pointing at the resolved file. No existing test in tests/unit/handlers/repo.test.ts exercises a symlink/case/relative-path divergence case for the non-git branch, so this bug is real, reachable, and untested -- correctly flagged, low severity is appropriate given it requires symlinks/case-divergence/relative input to trigger.

- **SH-009 fixed (Phase 8 Checkpoint F2)**: added a comment above `resolveSessionCwd`'s `while (candidate !== repoPath)` loop noting the string-equality comparison depends on both sides already being canonicalized (both derive from `classifyLocalPath`'s `canonicalPath`) — no logic change. Verified via `tsc --noEmit` and the full `vitest run` (444/444, including `tests/unit/handlers/terminal.test.ts` unchanged).

- **SH-006 fixed (Phase 8 Checkpoint F3)**: extracted `repoOpenBlocked(error)` and `repoOpenResult(params)` helpers in `repo.ts`, replacing the five inline `LocalActionResponse` literals in `repositoryOpenHandler` (matching the `mutationBlocked`/`folderMutationBlocked` pattern already used in file.ts/folder.ts). No behavior change — same fields, same conditional `repositoryRootPath` spread. Verified via `tsc --noEmit` and the full `vitest run`.

## Architecture Notes

This unit is a thin, fairly consistent Hono-handler layer that delegates all real logic to src/git/repo.ts, src/git/tree.ts, and services/* — a reasonable separation of concerns. Its main structural weakness is copy-pasted request-plumbing: JSON-parse-with-fallback, path normalization, branch resolution ("validateRepo ? ... : ''"), and error-response construction are each reimplemented per-handler (and per-file, since file.ts and folder.ts duplicate the same branch-resolution snippet independently) rather than sharing a small set of helpers, which is the unit's most consistent line-count/readability cost. A secondary, more concrete issue is response-status inconsistency in folder.ts: most mutation handlers return explicit 4xx/5xx on failure via folderMutationBlocked, but folderCreateChildHandler/folderInitRepositoryHandler/folderCloneRepositoryHandler always return HTTP 200 with an `ok:false` body — safe today only because the specific frontend callers happen to check the body's `ok` field instead of relying on fetch/mutate's res.ok-based throw, which is a fragile implicit contract worth documenting or unifying.
