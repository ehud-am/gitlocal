## Adjudication Log

- **SR-001 fixed (Checkpoint D6)**: rather than introducing a shared package (a larger architectural change out of scope for this checkpoint), `ui/src/types/index.ts` now sources its 87 wire-format-identical types (86 previously-duplicated names plus `SearchMatchType`, newly consolidated — see ui-types.md UT-001/UT-002) via a type-only `import type { ... } from '../../../src/types'` + bare `export type { ... }` re-export block, instead of redeclaring them. `src/types.ts` itself is unmodified — this is purely a UI-side change that reads from it. Verified empirically (not just by static reasoning) that `import type`/`export type` statements are fully erased under this project's TypeScript config (`ui/tsconfig.json`: `moduleResolution: "bundler"`) and introduce no bundler configuration change or runtime dependency on server code: `tsc --noEmit`, `vite build`, and the full `vitest run` (444/444) all pass unchanged, as do the root `npm run lint` and `npm run build` (confirming `src/types.ts` and the server bundle are unaffected). The two previously-differing types (`RepoLocationResponse`, JSDoc-wording-only difference; `SearchResult`, UT-001's inlined `matchType` literal) are now identical by construction since the UI consumes the server's exact declaration. Remaining UI-only types (ApiError, terminal-panel types, `ViewerState`, etc.) are untouched and still declared locally.
- **SR-002 fixed (Phase 7 Checkpoint E1)**: the SPA fallback route's `await import('node:fs').then((fs) => ...)` was replaced with a top-level `import { readFileSync } from 'node:fs'` and a synchronous handler body, removing the per-request dynamic-import/promise machinery. Behavior is unchanged (same try/catch fallback to the "UI not built" placeholder HTML). Verified via `tsc --noEmit`, the full `vitest run` (444/444), and root `npm run build`.

## Architecture Notes

This unit is a thin, well-organized composition root: cli.ts (process/CLI concerns), index.ts (a 7-line public library re-export barrel for the npm package entrypoint), server.ts (Hono app wiring plus a small amount of startup-path-classification business logic), and types.ts (589 lines of shared response/request contracts). The main structural concern is that server.ts mixes two responsibilities that could be split — pure route wiring/module state (createApp, get/setRepoPath etc.) versus non-trivial path-classification business logic (resolveOpenTarget, initializePaths, classifyServerError) that arguably belongs in a service module alongside git/repo.ts's classifyLocalPath, which it wraps. The single biggest architectural issue is the server/client type boundary: types.ts has no shared package with ui/src/types/index.ts, so ~80 request/response types are hand-copied verbatim on both sides of the JSON wire format, with the UI file's own comment admitting this is a known manual-sync liability (for terminal types, but the pattern is pervasive). A generated-types or shared-package approach at this boundary would remove a whole category of future drift risk. Module state (currentRepoPath, currentPickerPath, etc. in server.ts) is deliberately global/mutable, justified by a single-threaded comment, which is reasonable but constrains createApp to being effectively a singleton factory rather than a truly isolated app instance — worth flagging if multi-instance/testing-in-parallel needs ever arise.
