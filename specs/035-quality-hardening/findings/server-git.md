## Adjudication Log

- SG-005 (`src/git/tree.ts:41-45` sort vs `src/git/repo.ts` `listWorkingTreeDirectoryEntries` sort) — **REJECTED**: attempted the recommended `sortTreeNodes` extraction, standardizing both sites on `localeCompare`. This broke `tests/unit/git/tree.test.ts`'s "returns directories and files alphabetically within their groups" test — `localeCompare` and the manual `<`/`>` ternary order case-mixed names differently (e.g. `README.md` vs `main.ts` swap position), proving the two comparators are not behavior-equivalent despite the structural similarity. Per spec.md US4 Scenario 2, reverted both sites to their original, independent comparators rather than force a shared helper that changes real file-tree ordering for one call site.
- **SG-004 fixed (Phase 7 Checkpoint E1)**: `getTrackedPathType`, the private `isTrackedRepoPath`, and `classifyGeneratedLocalState` (all in `repo.ts`) each gained an optional trailing `trackedFiles?: string[]` parameter — when supplied, they read from the given array instead of independently spawning `git ls-files`/`git ls-files --error-unmatch`. All existing call sites that omit the parameter (`nearestExistingTrackedRepoPath`, the internal `repo.ts:1103` caller, and every test in `tests/unit/git/repo.test.ts`) are unaffected, since the default behavior when the parameter is omitted is unchanged. `tree.ts`'s three top-level search entry points (`searchWorkingTreeByName`, `searchWorkingTreeByContent`, `searchWorkingTreeScoped`) now call `getTrackedWorkingTreeFiles(repoPath)` exactly once per request and thread the resulting array down through the recursive `getSearchableWorkingTreeEntries` and through `matchesTrackedMode`/`classifyGeneratedLocalState`, instead of re-fetching it once per entry. Measured before/after on a synthetic 100-file/10-directory repo via a `PATH`-shimmed `git` wrapper counting real process invocations for one `searchWorkingTreeScoped` call: `git ls-files` spawns dropped from **320 to 1** (99.7% reduction); total git spawns for the request dropped from 557 to 238 (the remainder, 221 `rev-parse` calls from `validateRepo` and 11 `check-ignore` calls from `isIgnoredPath`, are outside this finding's described defect and are noted below as a follow-up candidate, not fixed in this checkpoint). Verified via `tsc --noEmit`, the full `vitest run` (444/444, including all of `tests/unit/git/repo.test.ts` and `tree.test.ts` unchanged), root `npm run build` (UI bundle 709.70 kB → 709.90 kB, a ~200-byte no-op delta), and `knip --dependencies` (no new findings).
- **Follow-up observation (not a fix in this checkpoint)**: the same before/after measurement above showed `classifyGeneratedLocalState`'s `validateRepo` call (itself a `git rev-parse` spawn) re-running on every invocation — 221 spawns for the same 100-file synthetic repo — plus 11 `git check-ignore` spawns via `isIgnoredPath` for untracked paths. Neither was described by SG-004's original evidence text, so per Phase 7's "no speculative optimization" rule this was left unfixed and flagged here as a candidate for a future, separately-adjudicated efficiency finding rather than folded into this checkpoint.
- **SG-001 fixed (Phase 8 Checkpoint F1)**: re-indented `listDir`'s loop body (`tree.ts:32-38`) to match the loop's actual brace nesting — purely cosmetic, confirmed no behavior change via `tsc --noEmit` and the full `vitest run` (444/444).

## Architecture Notes

This unit cleanly separates three concerns: identity-settings.ts (SSH key discovery/validation, no git dependency), repo.ts (the git command-execution core: config, branches, sync, working-tree mutation, path classification), and tree.ts (read-only tree listing/search built on top of repo.ts's primitives). The layering is sound — tree.ts imports from repo.ts and not vice versa, and identity-settings.ts is a leaf dependency of repo.ts. The main structural concern is repo.ts's size (~1836 lines, by far the largest file in the unit) and its low-level, uncached git-subprocess-per-call style: nearly every helper (getTrackedWorkingTreeFiles, isTrackedRepoPath, isIgnoredPath, getCurrentBranch, etc.) independently shells out to `git`, and higher-level functions compose several of these without any per-request memoization or batching layer. This is fine for single-shot calls (branch switch, commit) but becomes a real cost center wherever it's called in a loop, as documented in the efficiency finding above — a shared "git state snapshot" abstraction (already partially prototyped via `FileSyncAnalysis`/`buildFileSyncAnalysis`) could be extended to cover the tracked-file-list and ignore-checking paths used during tree crawling and search.
