# Phase 0 Research: Fix Empty Content on Startup

This feature is a bug fix in an existing, well-understood codebase, not a greenfield build. Research here consolidates the deep-dive investigation already performed (see spec.md's grounding) into concrete decisions, resolving every open technical question before design. There are no `NEEDS CLARIFICATION` markers in the Technical Context, so each topic below documents the chosen approach, its rationale, and alternatives considered rather than resolving an unknown dependency.

## 1. Server-side global error handling

**Decision**: Register a single Hono `app.onError(...)` handler in `src/server.ts`'s `createApp()` that catches any unhandled exception from a route handler and returns a structured JSON error body (see `contracts/error-response-contract.md`) with an appropriate status code, instead of falling through to Hono's default plain-text 500.

**Rationale**: `src/server.ts` currently registers no `onError` handler at all (confirmed by direct inspection — no `onError` call exists in the file). When a handler throws (e.g., a filesystem read failing), Hono's default response is a generic 500 with no machine-readable body. The frontend's `request<T>()` helper (`ui/src/services/api.ts`) tries to `res.json()` that response, fails, and produces a generic `{error: res.statusText, code:'UNKNOWN'}` — all detail about the real failure (permission denied vs. not found vs. unmounted) is lost before it ever reaches a component. A single global handler is the smallest change that preserves diagnostic detail end-to-end for every route, not just the ones this feature happens to touch.

**Correction confirmed during implementation**: the original plan assumed `request<T>()` also needed a code change to "preserve and surface" the `error`/`code` fields (tracked as task T006). On inspection while implementing, `request<T>()` already does this correctly and unmodified — `throw err` throws the parsed JSON body directly (`ui/src/services/api.ts:54-64`), so once the server (this item) returns a well-formed `{error, code}` body, the thrown value already has that exact shape with zero frontend changes. This was verified with two tests added directly against the unmodified code (`ui/src/services/api.test.ts`): one confirming a structured error body is thrown as-is, one confirming the existing generic-`UNKNOWN` fallback still applies when a response body genuinely isn't parseable JSON. T006 is retained in tasks.md as a verification task rather than an implementation task, matching the same pattern as research item #2's `readdirSync`/`realpathSync` correction — this feature has two internal gaps (server classification, UI error-state consumption) bridged by code that already existed correctly on both ends.

**Alternatives considered**:
- *Wrap every individual handler in its own try/catch*: rejected — duplicative, easy to miss a handler, and doesn't fix the root cause (Hono's default error response shape).
- *Have the frontend infer failure reasons from HTTP status codes alone*: rejected — status codes alone (e.g., generic 500) can't distinguish "permission denied" from "path vanished mid-request" with enough specificity for FR-005/FR-007's plain-language messaging requirement.

## 2. The non-git / generic-folder filesystem calls need no new try/catch — confirmed empirically during implementation

**Decision**: Do **not** add try/catch around `listWorkingTreeDirectoryEntries`'s `readdirSync` call (`src/git/repo.ts:1757`) or `canonicalizeExistingPath`'s `realpathSync` call (`src/git/repo.ts:289`). Leave both unguarded and rely entirely on the global `onError` handler (research item #1) to classify whatever propagates naturally.

**Rationale — corrected twice, the second time empirically during implementation**: An earlier draft of this decision proposed wrapping both calls in try/catch. A first correction (during Phase 1 design) rejected mirroring `getFastBrowseableRootEntryCount`'s "return 0 on failure" convention, since silently coercing a real read failure to an empty/zero result would reproduce the reported bug's symptom through a quieter mechanism, violating FR-004. That correction still assumed *some* form of try/catch (a "classify and rethrow" wrapper) was needed. During implementation, direct empirical testing against the installed `hono@4.12.23` package showed this assumption was unnecessary too:

```js
const { Hono } = require('hono')
const app = new Hono()
app.get('/boom-fs', () => { require('fs').readdirSync('/no/such/dir') })
// with NO app.onError registered:
await app.request('/boom-fs') // → status 500, and the thrown error (with .code === 'ENOENT' intact)
                               //   is exactly what a registered onError handler receives
```

Hono's internal dispatch already wraps every handler call in a try/catch and forwards the caught error — sync or async, framework-level or a raw Node `fs` error — to `app.onError` if one is registered, or to a generic default 500 responder if not. The raw `NodeJS.ErrnoException` thrown by `readdirSync`/`realpathSync` already carries its OS error code (e.g., `ENOENT`, `EACCES`) untouched all the way to that handler. So a try/catch inside `repo.ts` that only rethrows would be dead code with no behavioral effect — the classification research item #1 already needs to do (reading `err.code`) works identically whether the error was rethrown through an intermediate catch or propagated directly. Adding one anyway would contradict the project's own guidance against error handling for scenarios that don't need it, and would be exactly the kind of surface area a future contributor might "simplify" by adding a `return 0`/`return []` fallback — reintroducing the bug this feature fixes. Leaving the calls visibly unguarded, with a comment explaining why (see tasks.md T033), is the safer long-term state, not the riskier one.

This does **not** change the fix for the *actual* root cause: today, the read failure already produces a generic, unclassified 500 (confirmed above) because no `onError` is registered — research item #1 is what's still required and sufficient.

**Alternatives considered**:
- *Wrap both calls in try/catch that rethrows a reclassified error*: rejected after empirical verification — adds no behavior beyond what the natural throw + research item #1's `onError` classifier already provides, and increases the risk of a future accidental swallow-to-empty regression.
- *Mirror `getFastBrowseableRootEntryCount`'s "return 0 on failure" convention*: rejected (unchanged from the first correction) — would silently reintroduce the "looks empty" symptom and violates FR-004.
- *Proactively request macOS folder-access entitlements/usage descriptions so the permission prompt fires before first read*: valuable for the native app specifically but doesn't fix the underlying gap for the npm distribution, other OSes, or non-permission failures (deleted folder, unmounted drive); treated as an out-of-scope enhancement.

## 3. Verifying startup-folder candidates are actually enumerable

**Decision**: Change `isReadableDirectory` in `src/services/startup-preferences.ts` to also attempt a guarded directory read (not just `existsSync` + `statSync().isDirectory()`) before a folder is accepted as a startup default or "last used" folder in `resolveStartupFolder`.

**Rationale**: `isReadableDirectory` (lines 34-40) currently only checks existence and directory-ness. `stat` and `readdir` are gated separately by the OS in the exact scenario this feature targets, so a folder can pass this check and still throw the moment something actually tries to list it — which is exactly what happens today when `resolveStartupFolder` hands back a path it believes is safe.

**Alternatives considered**:
- *Leave `isReadableDirectory` as-is and rely solely on the guarded reads from research item #2 to catch the failure downstream*: rejected as insufficient alone — it would still let an unreadable folder be recorded as the "last used" preference (`writeStartupFolderPreference` also calls `isReadableDirectory` as its only gate), perpetuating the failure on every subsequent launch. Fixing the check at the source prevents an unreadable folder from ever being accepted as a startup candidate in the first place, in addition to (not instead of) guarding the downstream reads.

## 4. Frontend bootstrap (`['info']`) query failure handling

**Decision**: Add `isError` (and a retry affordance) to the `['info']` query in `ui/src/App.tsx`, and render an explicit failure screen — reusing the existing `ErrorScreen` component already defined in `App.tsx` (currently only used for the loading state) — instead of falling through to the full app shell with `info` undefined.

**Rationale**: Confirmed by direct inspection: the `['info']` query (`App.tsx:184-187`) destructures only `data`/`isLoading`. Once `isLoading` becomes `false` after a failed fetch (per the `retry: 1` global default in `ui/src/main.tsx`), execution falls past the `isLoading` check (`App.tsx:1038`) and the `info?.pickerMode` check (`App.tsx:1042`, both falsy/undefined on failure) straight into the main render path, where every `info?.x` access is silently `undefined` and the "ready for a first file" empty state (`info?.rootEntryCount === 0`) never engages (`undefined === 0` is `false`). The result is the full app shell rendering with no data and no error — precisely the reported symptom. `ErrorScreen` already exists and already matches the project's minimal, GitHub-inspired visual language (constitution Principle V), so extending its use is preferred over introducing a new presentation.

**Alternatives considered**:
- *Show a full-page native `alert()` or console-only error*: rejected — not discoverable by a non-technical user (constitution's target audience), and inconsistent with the existing in-page error banner pattern used elsewhere (`PickerPage.tsx`'s error banner, `FileTree.tsx`'s inline message).

## 4a. [Critical — discovered during hands-on implementation testing, not static inspection] React Query can pause a failed request forever, silently reproducing the exact bug

**Decision**: Configure the app's `QueryClient` with `networkMode: 'always'` (`ui/src/main.tsx`) and pin `focusManager.setFocused(true)` at startup (also `ui/src/main.tsx`).

**How this was found**: After implementing items #1, #4, and #5 above and manually verifying User Story 1 end-to-end in a real browser against a genuinely unreadable folder, the fix did not work — the app still rendered the old-looking "empty" dashboard instead of the new error screen, *despite* `/api/info` and `/api/tree` both demonstrably returning the correct structured 500. Direct inspection of the live query cache (`queryClient.getQueryCache().find({queryKey: ['info']}).state`) showed `status: 'pending'`, `fetchStatus: 'paused'`, `fetchFailureCount: 1` — the query had failed once, then tried to retry (per the app's `retry: 1` default), and React Query's retry-continuation logic (`query-core`'s `retryer.ts`, `canContinue()`) refused to continue because it requires **both** `onlineManager.isOnline()` (gated by `networkMode`, default `'online'`) **and** `focusManager.isFocused()` (gated by `document.visibilityState`/`document.hasFocus()`, with no `networkMode`-equivalent override) — and in the test environment, the tab was not focused. A query stuck in this state is neither `isLoading` nor `isError`, with `data` still `undefined` — the exact "isLoading: false, isError: false, data: undefined" limbo that produces the reported bug, and it is **completely independent of items #1–#5's fixes**, since it prevents `isError` from ever becoming `true` in the first place, regardless of how well the server classifies the failure or how correctly the UI branches on `isError`.

**Rationale**: GitLocal's frontend only ever talks to its own locally-spawned server on `127.0.0.1` — never the public internet — so the browser's general online/offline heuristic and window-focus state are both meaningless for deciding whether a request "should" be retried, and are actively harmful when they cause a real failure to hang silently instead of surfacing. This is significant beyond the specific permission-denied scenario tested: `networkMode: 'online'` pausing is a **known, real** category of unreliability in embedded WebKit contexts — precisely the situation for GitLocal's macOS native app distribution, where `WKWebView`'s `navigator.onLine`/focus/visibility signaling immediately after launch is a documented source of quirks. This makes it a highly plausible contributor to the *original* "many cases" framing of the reported bug, arguably more so than the specific filesystem-permission scenarios in items #1–#5, since it can silently swallow **any** query failure, at **any** time, independent of cause. Both settings are the standard, documented React Query recommendation for apps whose only backend is `localhost`.

**Verification**: Confirmed by manually reproducing in a real browser (permission-denied folder → correct "GitLocal couldn't load this workspace" / "Permission was denied while accessing this path." screen with a working "Try again" recovery action, verified via ref-based click, not just visual inspection) and via `ui/src/main.test.tsx`, which asserts `focusManager.isFocused()` stays `true` even when `document.visibilityState` is `'hidden'`, and that the exported `queryClient`'s default options carry `networkMode: 'always'`.

**Alternatives considered**:
- *Handle the "paused" `fetchStatus` case locally in each affected component (`App.tsx`'s `['info']`, `ContentPanel.tsx`'s `['tree']`)*: rejected — this is a systemic issue affecting every query in the app, not just the two this feature's user stories name; a per-query workaround would leave every other current and future query exposed to the same silent-limbo failure mode. Fixing it once, globally, at the `QueryClient` level is both simpler and strictly more robust.
- *Disable retries entirely (`retry: 0`)*: would sidestep the specific `canContinue()` pause (since there'd be no continuation to pause), but throws away the real value retries provide for genuinely transient local failures, and does not address `refetchOnWindowFocus`-adjacent behavior relying on the same focus manager elsewhere in the app.
- *Only set `networkMode: 'always'`, without the `focusManager` fix*: tried first, in isolation — confirmed insufficient by direct testing (the query still paused, since `canContinue()`'s focus check is unconditional and not gated by `networkMode` at all).

## 5. Content pane failure handling for the tree/folder query

**Decision**: Make `ContentPanel.tsx`'s root/default view (currently `if (!selectedPath) { ... return renderDirectoryList(...) }`) and its folder view (`if (selectedPathType === 'dir') { ... }`) both check `isDirectoryError` from the existing `['tree', ...]` query and render a genuine error state, mirroring `FileTree.tsx`'s already-correct `isError` handling for the identical query key.

**Rationale**: Confirmed by direct inspection: `ContentPanel.tsx` already destructures `isDirectoryError` from its `['tree', directoryPath, branch, refreshToken]` query, but only consults it in one narrow branch (the "local-only folder disappeared" case, gated additionally on `showSelectedLocalOnly`). The primary root/default view and the general folder view never check it, so a failed fetch renders identically to a successful-but-empty one — landing on the generic "This repository does not have any visible files yet" message. Meanwhile `FileTree.tsx` runs the *same query* and correctly shows "Failed to load file tree" on error. Aligning `ContentPanel.tsx` with the pattern already proven correct in `FileTree.tsx` is the minimal, consistent fix (also directly satisfies FR-003's cross-UI consistency requirement).

**Alternatives considered**:
- *Introduce a new shared hook/component for "tree query with error state" used by both `FileTree` and `ContentPanel`*: a reasonable refactor, but larger than this fix requires (per the project's guidance against premature abstraction); deferred as a possible follow-up, not required to satisfy the functional requirements.

## 5a. [Critical — discovered during hands-on implementation testing] The fallbackReason message never reached a real user, and the picker's own display of it was also broken

**Decision**: Three coordinated fixes, all found only by manually reproducing User Story 2 end-to-end against a real CLI launch (not by reading code or running unit tests against mocked API responses):
1. In `src/server.ts`, capture the `StartupFolderResolution` computed once at process startup (`cli.ts`'s `resolveStartupFolder()` call, before `createApp()`) into new module state (`getStartupFolderResolution`, mirroring the existing `currentStartupOpenTarget` pattern), and have `startupFolderHandler` (`src/handlers/repo.ts`) return that captured snapshot instead of recomputing fresh.
2. In `src/services/startup-preferences.ts`, add a small `describeUnreadableFolder(path)` helper that distinguishes "no longer exists" vs. "permission denied" vs. "currently unreachable" (disconnected drive), and use it to build the `'platform-default'` tier's `fallbackReason` in `resolveStartupFolder` — directly satisfying US2 Acceptance Scenario 2's requirement that the message be "distinct from 'deleted' or 'permission denied'."
3. In `ui/src/components/Picker/PickerPage.tsx`'s `startupMessage`, fix the `'platform-default'` branch to actually use `startupFallbackReason` (it was hardcoded to a generic message, silently discarding the fetched reason — the `'home-fallback'` branch right next to it already did this correctly). In `ui/src/App.tsx`, add a `['startup-folder']` query and a one-time effect that sets `statusMessage` from `fallbackReason` when present and the app is not in picker mode.

**How this was found**: After implementing what looked like a complete US2 fix (an earlier version of finding #2, without the reason-classification, and PickerPage's message fix), manually reproducing the scenario end-to-end (remember a folder, delete it, relaunch with no explicit path) showed **no message anywhere** — the app silently opened the Documents fallback with a normal-looking app shell, exactly the reported bug. Investigation revealed two independent problems: (a) `cli.ts` calls `rememberStartupFolder(launchPath, ...)` immediately after resolving the startup folder and before the HTTP server even starts listening — this overwrites the "last used" preference file with the *new* (fallback) path, so by the time any client queries `/api/startup-folder`, `resolveStartupFolder()` recomputes fresh from the *already-mutated* file and finds nothing wrong, permanently erasing the fallback evidence before the UI ever has a chance to fetch it; and (b) even where the UI *did* have the right data (verified via direct `curl`), the successful-fallback case (`pickerMode: false`, a real folder resolved and opened) never renders `PickerPage` at all — that component is reached only via explicit "leave repository"/browse-outside-scope actions, not the default startup path — so a fallbackReason fix confined to `PickerPage` would only ever be exercised by unit tests with mocked API responses, never by a real user hitting this scenario through the actual default launch flow that spec.md's User Story 2 describes.

**Rationale**: Both problems share the same root cause as this feature's other findings — a control-flow detail with no automated-test signal at the unit level (since unit tests mock the API and never observe the mutate-then-recompute race in item (a), and no existing test rendered `App.tsx` in its default, successfully-resolved-but-fallback-triggered state to notice `PickerPage` isn't involved in item (b)). Fixing (a) requires preserving the one-time computation for the life of the server process — the identical pattern already used for `currentStartupOpenTarget`, extended consistently rather than inventing a new mechanism. Fixing (b) requires surfacing the information where the user actually is (the main app view), not only in a component that a successful, ordinary launch never renders.

**Verification**: Confirmed via `tests/unit/services/startup-preferences.test.ts` (three new tests for the deleted/permission-denied/disconnected distinction), `ui/src/components/Picker/PickerPage.test.tsx` (fallbackReason now renders in the `platform-default` branch, plus a same-path-reopens-successfully recovery test), `ui/src/App.test.tsx` (fallbackReason renders as a status banner in the main app view), and a full manual reproduction: remembered folder deleted → relaunch → real browser shows "Last used folder no longer exists." as a banner atop the Documents fallback view, matching spec.md's User Story 2 exactly.

**Alternatives considered**:
- *Stop `rememberStartupFolder` from running automatically on every successful resolution, only on explicit user actions*: rejected — a broader behavior change than this feature's scope, with unclear consequences for other existing flows (e.g., cwd-detected current-repo launches) that also rely on this side effect.
- *Only fix `PickerPage.tsx`'s existing bug, without adding the `App.tsx` surface*: rejected once end-to-end testing showed `PickerPage` is not reached in the primary scenario spec.md describes — this would have shipped a fix that only ever ran in tests, never for a real user.

## 6. Explicit/remembered path failure surfacing — corrected after empirical testing (cli.ts/server.ts needed no change; the gap was solely in PickerPage.tsx)

**Original decision (Phase 1 design, based on static inspection alone)**: assumed `src/cli.ts`'s `explicitFileLaunch` classification and `src/server.ts`'s `initializePaths` silently dropped the failure when an explicit path didn't exist, requiring changes to both.

**Correction (made during implementation, by directly running the real CLI against a missing path and inspecting the live API response rather than trusting the earlier static reading)**: `cli.ts`'s current classification (`explicitFileLaunch = explicitClassification?.pathType === 'file' || (repoPath && !explicitClassification?.exists)`) already evaluates to `true` for a missing path, which already causes `initialOpenSource: 'explicit-launch'` to be passed to `createApp()`. Inside `initializePaths`, this already routes through `resolveOpenTarget`, which already sets `currentStartupOpenTarget` to `{status: 'failed', message: 'Path does not exist: …'}` — **before** falling back to `currentPickerPath = process.cwd()`, not instead of it. This is already covered by a pre-existing test (`tests/unit/handlers/repo.test.ts`, "returns distinct startup-open failure targets for missing and unsupported files"), and was reconfirmed live: `node dist/cli.js /tmp/definitely-missing-path` followed by `curl /api/startup-open-target` returns exactly this structure. **Neither `cli.ts` nor `server.ts` needed any change for this scenario.**

The one real, confirmed gap was entirely on the frontend: `ui/src/components/Picker/PickerPage.tsx` never called `api.getStartupOpenTarget()` at all — not "computed but not displayed" as the original research item assumed, but never fetched in the first place. (`App.tsx` does compute a failure message via `applyOpenFailure`/`setStatusMessage` for the non-picker-mode case, but that logic is simply unreachable once `info?.pickerMode` is true and `<PickerPage/>` renders instead — a correct observation from the original research, just not the whole picture, since the picker itself had never been taught to ask the same question.)

**Decision (as actually implemented)**: In `ui/src/components/Picker/PickerPage.tsx`, add a call to `api.getStartupOpenTarget()` in `loadPath()`'s initial-load branch (alongside the existing `getStartupFolder()` call), store the result in new `openTargetMessage` state, and render it via a `role="alert"` element whenever `target.status !== 'accepted'`.

**Alternatives considered**:
- *Redirect to an error page instead of the picker when the explicit path is invalid*: rejected — the picker is already the correct recovery surface (it lets the user choose a valid folder); the fix is to make the picker show *why* it's there, not to replace it.
- *Fix this by changing `cli.ts`/`server.ts` per the original plan*: rejected after empirical verification showed there was nothing to fix there — doing so anyway would have been unnecessary churn to already-correct code.

## 7. Manual browser-open fallback messaging (npm/terminal distribution) — and a far more severe crash bug found underneath it

**Decision**: When `openBrowser()` in `src/cli.ts` fails to launch a browser, print an explicit, prominent terminal instruction telling the user to open the logged local address manually, in addition to (not instead of) the existing "gitlocal listening on ..." log line. Additionally — found only by forcing a real failure rather than reading the code — attach an `'error'` listener to the `ChildProcess` that `open()` returns, since without one, a real spawn failure crashes the entire GitLocal server, not just the browser tab.

**Rationale, part 1 (as originally scoped)**: Confirmed by direct inspection: `openBrowser()`'s catch block was empty aside from a code comment ("non-fatal — user can open browser manually"); nothing new was printed when this happened. This produces the same "nothing seems to have happened" symptom as the main bug, scoped to the npm/terminal distribution only.

**Rationale, part 2 — discovered while verifying part 1 empirically**: Simply adding a `console.log` in the existing `catch` block was not enough, and manually forcing a real browser-open failure (by restricting `PATH` so the `open` npm package's underlying `spawn('open', …)` call gets `ENOENT`) proved this beyond doubt: the process crashed with `Error: spawn open ENOENT` and an "Unhandled 'error' event" stack trace, **bypassing the `try/catch` entirely** and taking down the whole server, not just the browser tab. Tracing into `node_modules/open/index.js` explains why: `open()`'s default call shape (no `{wait: true}` option, which is how `openBrowser` calls it) does not return a Promise at all — it calls `subprocess.unref()` and returns the bare `ChildProcess` synchronously. Only the `options.wait` branch attaches a `.once('error', reject)` handler. Since `openBrowser` does `await open(url)` with no `wait` option, the `await` immediately resolves to that plain `ChildProcess` (awaiting a non-thenable is a no-op), and the `try/catch` block has already exited by the time the child process actually fails to spawn on a later tick — an asynchronous 'error' event with zero listeners, which is a fatal, uncatchable-by-`try/catch` condition by Node's own `EventEmitter` semantics for the special `'error'` event. The fix is to explicitly attach `.once('error', …)` to the returned `ChildProcess` after awaiting `open()`, converting what was an application-crashing bug into the originally-intended non-fatal message.

**Why this matters beyond scope**: this is more severe than the "P4, low-frequency" framing spec.md gave User Story 4 — a missing/misconfigured browser opener doesn't just fail to open a tab, it takes the entire local server down, which would look exactly like "GitLocal doesn't work at all" to an affected user (any environment without a default browser handler registered, not only exotic ones). It was found only because this feature's process included forcing the actual failure condition end-to-end rather than stopping at "the catch block now logs something."

**Alternatives considered**:
- *Attempt a second/different browser-launch strategy automatically*: rejected as out of scope — the fix here is about feedback (and, as it turned out, crash-safety), not about improving auto-launch success rate itself.
- *Trust that the try/catch already handled this, since `open()` is awaited inside it*: this was the original, incorrect assumption — disproven by directly forcing the failure rather than reasoning about it statically, consistent with this feature's recurring lesson that this class of bug does not show up under static reading or mocked unit tests.

No `NEEDS CLARIFICATION` markers remain. All seven decisions above are grounded in direct inspection of the current code (not assumption), and each maps directly to one or more functional requirements in spec.md (FR-001 through FR-009). Phase 1 design proceeds using these decisions as given.
