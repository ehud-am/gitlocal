# GitLocal v0.10.0 Release Review

## Scope

- Release: `v0.10.0` — the first official release of the integrated terminal panel across **both** distributions (npm and the macOS Homebrew app).
- Branch: `release/0.10.0`, cut directly from `main` (which already contains the terminal panel feature from `v0.9.17`).
- No product/server/UI code changes since `v0.9.17`. This release exists solely to fix a macOS packaging script bug that blocked `v0.9.17`'s Homebrew build.
- Release date: 2026-08-09

## Background

`v0.9.17` published the terminal panel feature to npm successfully, but its Homebrew/macOS leg failed in CI at the "Validate app package" step, before the GitHub Release or the push to the `homebrew-gitlocal` tap repo ran — so neither of those happened. Since npm publishes are immutable and the `v0.9.17` tag's commit was already consumed by a real (partial) publish, the fix is shipped as a new version rather than by moving the existing tag.

## Root Cause

`packaging/macos/release/test-package.sh` gained a new verification block in `v0.9.17` (commit `f72c72f`) that directly imports `node-pty` from inside the packaged app to confirm the native binding is actually bundled correctly — see the comment at `test-package.sh` explaining why the `/api/info` smoke test alone can't catch this. That block runs in a subshell: `cd "${APP_PATH}/Contents/Resources/gitlocal/dist"` and then re-references `"${APP_PATH}/Contents/Resources/runtime/node"`. `APP_PATH` defaulted to a **relative** path, so after the `cd`, the second reference to `APP_PATH` no longer pointed at the app bundle — it failed with `No such file or directory`, which the script (correctly, if confusingly) reported as `Packaged node-pty failed to load`. The underlying node-pty packaging was not actually broken; the verification script itself had the bug.

## Fix

- `packaging/macos/release/test-package.sh`: resolve `APP_PATH` to an absolute path immediately after it's set, before any `cd`, so every later reference (including inside the node-pty-check subshell) resolves correctly regardless of working directory.
- A contrarian QA pass on that first fix (see below) found that the initial resolution approach (`cd "$(dirname ...)" && pwd` concatenated with `basename` into a single assignment) would silently produce a bogus path instead of failing loudly if the app bundle didn't exist yet, because `set -e` doesn't trip on a command substitution failure inside a larger assignment expression. Fixed by explicitly checking `test -d "${APP_PATH}"` first and exiting with a clear error before attempting resolution, then resolving directly via `cd "${APP_PATH}" && pwd` (simpler than the dirname/basename split, since `APP_PATH` is itself the directory).

## Verification Reviewed

- `npm run lint` (`tsc --noEmit`): clean.
- `npm run test:server`: 430/431 passing. The one failure (`tests/integration/terminal.test.ts`) is the same known, pre-existing sandbox-only proxy/loopback-fetch limitation disclosed in the `0.9.17` release review — unrelated to this branch's changes (which don't touch server code).
- `npm run test:ui`: 421/421 passing, coverage gates intact.
- `npm run build`: server + UI bundles build cleanly.
- `npm run audit` / `npm run audit:ui`: 0 vulnerabilities in both.
- The macOS packaging script itself cannot be executed in this Linux sandbox (it depends on `codesign`, `PlistBuddy`, and a macOS app bundle); the fix was instead verified by reproducing the exact bug and its resolution in an isolated shell harness (relative-path-across-`cd` failure, then success after the fix; and the missing-bundle edge case failing loudly with the corrected version) before and after each commit.

## Contrarian QA Findings

Scope: this pass reviewed only the packaging fix and 0.10.0 release-readiness — the terminal feature itself (session limits, WebSocket payload caps, focus management, path sandboxing, accessibility) was already reviewed in full for `0.9.17` and is unchanged here.

1. **[Blocker, fixed]** The first version of the `APP_PATH` fix didn't fail loudly on a missing app bundle — `set -e` doesn't trigger on a command substitution failure embedded inside a larger assignment expression, so a missing build directory would silently collapse `APP_PATH` to `/GitLocal.app` and produce a misleading downstream error instead of a clear one. Not reachable via the current CI workflow (which always runs `package-app.sh` immediately before `test-package.sh`, guaranteeing the directory exists), but a real robustness gap for any manual/local invocation. Fixed with an explicit existence check before path resolution.
2. **[Low, no fix needed]** The same "relative path before a `cd`" shape appears in `packaging/macos/release/package-app.sh:62` and `packaging/macos/cask/test-install-cask.sh:27`, but both were confirmed safe on inspection — `package-app.sh`'s `APP_PATH` is already built from an absolute `ROOT_DIR`, and `test-install-cask.sh` only resolves an already-validated path. No other instance of the anti-pattern found across `packaging/macos/` or the release workflows.
3. **[Positive]** Version consistency confirmed: `package.json` and `package-lock.json` (root and nested) are `0.10.0`; `ui/package.json`'s independent `0.1.0` version is unused by any release script and pre-existing, not a release concern.
4. **[Positive]** Tag/publish sanity confirmed: `publish.yml` fails fast if the pushed tag doesn't match `package.json`'s version; nothing in the npm publish or Homebrew cask update path assumes anything about the numeric shape of the previous version, so skipping `0.9.18` and going straight to `0.10.0` is safe.
