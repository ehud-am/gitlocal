# GitLocal v0.9.16 Release Review

## Scope

- Release: `v0.9.16` — infra/packaging hotfix, no product code changes.
- Branch: `fix/macos-libnode-packaging` (not yet merged to `main` at time of writing).
- Fixes the macOS native app packaging failure that has blocked `publish-homebrew` on the last three releases.
- Release date: 2026-08-04

## Background

`publish-homebrew` (the second job in `.github/workflows/publish.yml`, gated on `publish-npm` succeeding) has failed for three consecutive releases, each for a different, unrelated reason:

- 0.9.13: `gh` CLI `Not Found` error on a repo lookup.
- 0.9.14: `HTTP 422 tag_name was used by an immutable release` — a stale/blocked GitHub Release for that tag.
- 0.9.15: `Unable to locate the Node shared library at .../lib/libnode.137.dylib` — the actual bug this release fixes.

The 0.9.13 and 0.9.14 failures were not investigated further as part of this release; they are historical and superseded by this fix. Only the 0.9.15 root cause was diagnosed and addressed.

## Root Cause

`packaging/macos/release/package-app.sh` required a `libnode.<ABI>.dylib` file to exist next to the `node` binary provided by `actions/setup-node`, and copied it into the packaged app's `runtime/` resources. Newer Node.js 24.x macOS builds (specifically 24.18.0, used by `publish.yml` via `actions/setup-node@v6` with `node-version: 24`) no longer ship this file, so the script failed outright before ever reaching `xcodebuild` output packaging.

Inspection of the native macOS wrapper (`native/macos/GitLocal/GitLocal/GitLocalService.swift`, `BundlePaths.swift`) confirmed the app only ever spawns the bundled `runtime/node` binary as a subprocess (`process.executableURL = paths.nodeRuntime`) — it never dlopens or links against `libnode.dylib`. The shared library was dead weight, not an actual runtime dependency.

## Fix

- `packaging/macos/release/package-app.sh`: removed the `libnode.*.dylib` lookup/copy step; only the `node` binary itself is copied into `runtime/`.
- `packaging/macos/release/test-package.sh`: removed the corresponding dead assertion that the shared library exists in the packaged app.
- `.github/workflows/macos-app-release.yml` (the `workflow_dispatch`-only artifact-build workflow, used here as a safe test harness): aligned its Node setup (`actions/setup-node@v6`, `node-version: 24`) with `publish.yml`'s real `publish-homebrew` job. It previously ran Node 22, which does still ship `libnode.dylib` — meaning an earlier validation pass on this workflow would not have actually reproduced the failure. This is a genuine gap, described below.

## Verification Reviewed

- `npm run verify` passed on the branch: full test suite, build, both audits (0 vulnerabilities each).
- Two independent `macos-app-release.yml` dispatch runs on `macos-latest`, exercising the real packaging + `test-package.sh` functional smoke test (spawns the packaged `runtime/node` binary, curls `/api/info`):
  - Run 30872424010 (commit `61d8e73`, core fix only) — Node 22, succeeded. Insufficient on its own; see Contrarian QA below.
  - Run 30872807055 (commit `a12b7f5`, fix + Node-24 alignment) — confirmed via job step list to run `actions/setup-node@v6` with Node 24, matching `publish.yml` exactly. Succeeded, including `Validate app package`. This is the run that actually reproduces and confirms the fix against the real failure condition.

## Contrarian QA Findings

A contrarian QA sub-agent reviewed this fix, scoped narrowly to the 2-file packaging diff (proportionate to a small, mechanical hotfix rather than a full-feature review), assuming a regression exists and attempting to disprove release-readiness:

- Flagged that the validation run cited as proof of the fix (`macos-app-release.yml`, run 30872424010) used `actions/setup-node@v4` with `node-version: 22`, while the actual failing job in `publish.yml` uses `node-version: 24` — the exact version whose macOS build dropped `libnode.dylib`. The Node-22 run therefore did not exercise the real failure condition and did not prove the fix works under it.
  - Result: Fixed. Updated `macos-app-release.yml` to `actions/setup-node@v6` / `node-version: 24`, matching `publish.yml`, and re-ran validation (run 30872807055, see above) — genuinely confirms the fix.

No other findings; the diff is small and mechanical (remove a dead dependency and its corresponding test assertion).
