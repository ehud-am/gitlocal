## Summary of changes

- **Footer external links (native macOS)**: the embedded `WKWebView` had no navigation-policy handler for external/new-window navigation, so clicking the GitHub or gitlocal.dev footer links silently did nothing in the native app (already worked in the npm/browser distribution). Added `webView(_:decidePolicyFor:decisionHandler:)` in `ViewerWindowController.swift`, routing such navigation to `NSWorkspace.shared.open` instead of letting it fall into the void.
- **Footer visual pattern**: restyled with paired icons (new `GitHubIcon`/`GlobeIcon` in `ui/src/components/ui/icons.tsx`) in a compact, muted developer-tool-footer treatment, with visible hover/keyboard-focus states.
- **PPTX preview — OOXML inheritance**: `PptxViewer.tsx` now resolves placeholder geometry and background fill through the slide→layout→master inheritance chain (previously only a slide's own direct XML was ever read, so anything beyond a trivial from-scratch deck rendered incorrectly).
- **PPTX preview — theme colors**: backgrounds and run colors set via a theme reference (`a:schemeClr`, e.g. "Background 1"/"Accent 1" — the form real-world decks actually use, not literal RGB) are resolved through the slide master's `<p:clrMap>` and its `<a:theme>` part's `<a:clrScheme>`, including the `a:sysClr`/`lastClr` color form. This was the root cause of the originally reported bug (a real Microsoft-published sample deck's background rendering as nothing).
- **PPTX preview — layout/master decorative content**: non-placeholder shapes (logos, background graphics, static captions) defined directly on a slide's layout/master now render, composited master-under-layout-under-slide to match PowerPoint's own rendering order. Hidden (`hidden="1"`) shapes are skipped. EMF/WMF images (no browser-native decoder) render as "not available in this preview" instead of a broken image.
- **PPTX preview — continuous scroll**: replaced Previous/Next button pagination with all slides in one scrollable list, an `IntersectionObserver`-driven "Slide N of M" position indicator (scoped to the actual scroll container, not the page viewport), and inline per-slide speaker notes.
- **PPTX preview — responsive sizing**: the slide canvas is measured via `ResizeObserver` and scaled via CSS `transform` to fill the available panel width, instead of a fixed-pixel canvas that could overflow a narrower panel.
- **Version/changelog**: `package.json`/`package-lock.json` bumped to `0.13.4` (root only — `ui/package.json` stays at its own independent, never-published `0.1.0`, matching every prior release); `CHANGELOG.md` updated with all of the above.

This feature had two rounds of post-implementation follow-up (documented in `specs/043-footer-pptx-fixes/tasks.md`'s "Post-Implementation Follow-Up" sections) driven by testing against a real-world sample deck (Microsoft's own "Get started with Microsoft 365 Copilot in PowerPoint") after the initial implementation — first the theme-color/responsive fixes, then the layout/master decorative-content fix — each independently verified against that same real file via a local server + browser before moving on.

## Contrarian QA Review

Per Constitution Principle VIII, ran 8 independent review passes (as separate agents, each with no visibility into the others' findings) over the full diff since the previous release: three correctness angles (line-by-line diff scan; removed-behavior audit — for every deleted/replaced line, verify its invariant was re-established; cross-file caller/callee trace), three cleanup angles (reuse of existing helpers; simplification; efficiency), one altitude angle (root-cause-vs-bandaid), and one CLAUDE.md-conventions angle. This is a genuinely adversarial pass, not a rubber stamp — it found real issues, five of which were fixed before merging (commit `10e5c1e`) and several of which are deferred as documented follow-up work.

### Fixed before release

1. **Keyboard-only navigation was silently broken.** The old paged view's Previous/Next buttons were the only keyboard-operable affordance for moving between slides; the continuous-scroll rework removed them without replacing that affordance — the new scroll container had no `tabIndex` and no shape inside it was focusable, so a keyboard-only user had no way to reach any slide beyond whatever the initial viewport showed. **Fix**: each slide item is now individually focusable (`tabIndex={0}`, `role="group"`, `aria-label="Slide N of M"`), so Tab walks through every slide, and the browser's native focus-scroll-into-view brings each into the viewport as it's reached. Verified in-browser against the real sample deck: Tab-ing through reliably reached and displayed all 10 slides, with the position indicator tracking correctly. (An initial attempt — `tabIndex` on the scroll container itself, intending native arrow/Page-key scrolling — was tested in-browser and found *not* to work: a focused-but-not-itself-scrollable element doesn't forward Page Down/arrow keys to a scrollable ancestor in real browser behavior, only a one-time "scroll into view" on focus. Caught by testing the fix, not just reading the code — see `specs/043-footer-pptx-fixes/tasks.md` for the full account.)
2. **The `IntersectionObserver` root lookup was a fragile, wasteful DOM/CSS-sniffing walk.** `findScrollableAncestor` walked `parentElement` calling `getComputedStyle(node).overflowY` at each level to find "whatever scrolls" — but the answer is always the same, known element (`.content-panel-selection-root`, `ContentPanel`'s own scroll wrapper, shared by every preview type). This both forced a redundant style recalculation on every one of N slide items' mount (for a large deck, N wasted top-to-root walks converging on one node) and was fragile to any future CSS change unrelated to this component (e.g. a wrapper regaining an `overflow` rule). **Fix**: `element.closest('.content-panel-selection-root')` — a single, fast, native lookup by the actual known class, matching what this component's own CSS comment already documented.
3. **`matchPlaceholder`'s type-fallback could bind two unrelated placeholders together.** When a slide placeholder has neither `@idx` nor `@type` (a valid, non-rare OOXML form for body/content placeholders), the fallback matched any layout/master candidate with `type: null` too — i.e. `null === null` — which, if a layout defines more than one such untyped/unindexed placeholder, could silently inherit the wrong one's geometry with no error signal. **Fix**: the type-based fallback now requires a non-null `@type` on both sides; two doubly-ambiguous placeholders no longer match by coincidence (falls back to the slide's own direct geometry instead, the pre-existing safe default for "no match").
4. **Hidden layout/master placeholder shapes weren't filtered from the inheritance-candidate list.** The `hidden="1"` filter was applied to non-placeholder decorative shapes but not to placeholder shapes before they were added as `matchPlaceholder` candidates — a hidden legacy placeholder sharing an `@idx`/`@type` with a visible one could be matched instead, silently mispositioning the slide's actual placeholder content. **Fix**: the same hidden-shape check now runs before a shape is classified as placeholder-or-decoration, not only in the decoration branch.
5. **The native macOS external-link check was narrower than documented.** `research.md` §5 specified detecting `targetFrame == nil || targetFrame?.isMainFrame == false`; the shipped code only checked `targetFrame == nil`. Low real-world impact today (the app has no iframes), but a real gap between documented intent and implementation. **Fix**: matched the guard to the documented condition.

All five fixes were re-verified: `npm run verify` (full test/build/audit) passed clean after, `cd ui && npx tsc --noEmit` clean, a new test locks in the keyboard-focusability behavior, and `xcodebuild` succeeded for the Swift change.

### Deferred as follow-up (not blocking this release)

These are real, verified-plausible findings that don't regress anything this release shipped — they're gaps beyond what was reported/verified against the actual real-world file this release was built to fix, or pure cleanup with no behavior risk. Each has been filed as a standalone follow-up task:

- **`<p:bgRef>` themed backgrounds unhandled** — `parseBgFill` resolves the `<p:bgPr><a:solidFill>` background form (including theme-scheme colors, this release's fix) but not the second, mutually-exclusive OOXML form, `<p:bgRef idx="N">` (an index into the theme's background-fill-style matrix) — the form PowerPoint writes for "Design Ideas"/background-gallery themed backgrounds. The real sample file this release was verified against uses `bgPr`, not `bgRef`, so this wasn't caught by manual verification; it's the same class of "background renders as nothing" bug, just a different encoding, and worth a dedicated follow-up rather than scope-creeping this release further.
- **Grouped shapes (`p:grpSp`) are entirely unparsed** — any shape a deck author grouped (a very common authoring action) is completely invisible in the preview, with no placeholder or signal. Explicitly out of scope per `research.md` §4 (the one group found in the real sample file was a hidden design-grid layer, not user content), but the reviewer's point that *any* grouped user content silently vanishing is real and worth addressing stands.
- **EMF/WMF gate is a blocklist of the two formats the sample deck hit, not a renderable-format allowlist** — `.tiff` (already in `extToMime`'s map, unaffected by this release) isn't reliably `<img>`-renderable in Chrome/Firefox either but isn't gated; compressed metafile variants (`.emz`/`.wmz`) aren't in the format map at all and bypass the gate, falling through to a browser-broken-image icon instead of the graceful placeholder. Minor; not a regression.
- **Parsing duplication and eager image loading** — several independent review angles converged on: a relationship-XML-parsing loop repeated 4 times across `findRelTarget`/`loadPartIndex`/`parseSlide`/`parsePresentation`; a near-identical picture-parsing loop duplicated between `loadPartIndex` and `parseSlide`; three cache `Map`s threaded as separate function parameters where one bundled object would do; and — the most substantive of this group — every embedded image (slide content and layout/master decorations alike) being base64-decoded eagerly during the initial full-deck parse, before any slide is shown, which undercuts this same release's own `IntersectionObserver`-based deferred-rendering design for large, image-heavy decks. All real, none behavior-affecting; filed as one cleanup follow-up.

No other correctness issues survived verification. The CLAUDE.md-conventions pass found zero violations.

## Residual Risk

- **The three deferred contrarian-QA follow-ups above** (`p:bgRef` themed backgrounds, `p:grpSp` grouped shapes, parsing-duplication/eager-image-loading cleanup) are filed as standalone follow-up work, not fixed in this release. None regress previously-working behavior; they're gaps in the new PPTX rendering capability itself, beyond what the originally reported bug (and its real-world verification file) required.
- **Native macOS keyboard-navigation fix has not been exercised by a human**, nor via the native `WKWebView` at all — verified via the npm/browser distribution's real Chromium-based preview only (Tab-ing through the deck reached all 10 slides correctly there). The underlying DOM/JS behavior is identical in both distributions (same React bundle), so this is low risk, but a native-app click-through wasn't performed, consistent with this repository's established pattern for UI changes verified without macOS Accessibility/screen-recording access (see the v0.13.3 review's identical caveat for the About-panel change).
- **Publication status**: verification and contrarian QA complete on `release/v0.13.4` at commit `10e5c1e`. **Not yet merged into `main`, tagged, or published.** Tagging and pushing `v0.13.4` triggers `.github/workflows/publish.yml` (publishes to the public npm registry, builds and attaches a macOS artifact to a new GitHub release, pushes an updated cask to the external `ehud-am/homebrew-gitlocal` tap) — this is a separate, explicit step not taken as part of this review.
