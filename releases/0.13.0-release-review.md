# GitLocal v0.13.0 Release Review

## Scope

- Release: `v0.13.0` — the `039-bugfix-pptx-preview` spec (four security/correctness/reliability bug fixes plus a new read-only PPTX preview capability), **plus a standalone addendum fixing a long-standing "empty folder on launch" problem** (not part of any numbered spec; added to this same release after the spec-039 review below was already written).
- Branch: `039-bugfix-pptx-preview` (uncommitted working-tree changes against `main` at time of the spec-039 review; the addendum below was committed afterward). 17 tracked files changed for spec 039 plus new files: `ui/src/components/ContentPanel/PptxViewer.tsx`/`.test.tsx`, 13 fixture `.pptx` files, and `specs/039-bugfix-pptx-preview/`. The addendum additionally touches `src/server.ts`, `src/services/startup-preferences.ts`, `src/handlers/repo.ts`, `src/types.ts`, and `ui/src/components/Picker/PickerPage.tsx`.
- Review date: 2026-09-04 (spec 039); 2026-09-05 (startup-fallback addendum)

## Summary of changes

- **US1 (bug fix)**: repository write-path containment (`resolveSafeRepoPath` in `src/git/repo.ts`) now re-checks for a symlink escape on every intermediate path segment, and immediately before `mkdir`/`writeFile`, rather than only at the final resolved path.
- **US2 (bug fix)**: branch-search path parsing (`src/handlers/search.ts`) switched from splitting on `:` to a length-based `${branch}:` prefix strip, so filenames containing a colon are no longer misparsed as a branch delimiter.
- **US3 (bug fix)**: changed-file review (`src/git/repo.ts`, `getWorkingTreeChangeDetails`) now reads `git status` via `--porcelain=v1 -z` (NUL-delimited records) instead of the newline-delimited default, sidestepping Git's C-quoting of renamed paths (spaces, non-ASCII, quote/backslash characters) entirely rather than decoding it.
- **US4 (bug fix)**: non-terminal WebSocket upgrade attempts (`src/terminal/websocket.ts`) now get an immediate `404` + `socket.destroy()` instead of being left open.
- **US5 (new feature)**: read-only PPTX preview (`PptxViewer.tsx`), via lazily-loaded `jszip` + `fast-xml-parser`, rendering each slide as a best-effort formatted view — positioned text runs, background fill, embedded images — with next/previous navigation and a speaker-notes panel, wired into the existing preview registry with zero changes to `ContentPanel`'s dispatch logic. Pixel-faithful rendering is explicitly out of scope (no free/license-compatible renderer exists), matching spec 038's chart-data-as-table tradeoff.

## Pre-Release Contrarian QA (this review)

Per Constitution Principle VIII, three independent contrarian-QA sub-agents reviewed the full working-tree diff against `main` ahead of this release, each assuming regressions exist rather than presuming readiness: one covering bugs/security, one covering performance/dead-code/efficiency, one covering accessibility.

**Findings, both fixed before release:**

1. **[Documentation inaccuracy + untested edge case, fixed]** `CLAUDE.md`'s "Recent Changes" entry claimed the US3 fix added "a new `unquoteGitPath` helper" to decode Git's C-quoted rename paths. No such helper exists anywhere in the diff or codebase — the actual fix instead switches to `git status --porcelain=v1 -z`, which sidesteps C-quoting entirely rather than decoding it (a valid, arguably simpler approach, but not what was documented). The only test exercising this path covered a rename with a space, not the non-ASCII/quote-character cases FR-008 and spec.md's edge cases explicitly call out. **Fix**: corrected the `CLAUDE.md` entry to describe the actual `-z` porcelain approach, and added a test (`tests/unit/git/repo.test.ts`, "preserves non-ASCII and quote characters in renamed changed-file paths") covering a renamed path with a café/quote-character mix. All 108 tests in that file pass.

2. **[Accessibility gap, fixed]** `PptxViewer.tsx` had zero automated accessibility test coverage — no `jest-axe` assertion anywhere in `PptxViewer.test.tsx`, and `ContentPanel.test.tsx`'s two existing `axe()` assertions never render a `.pptx` file. This is an established, already-wired pattern elsewhere in the repo (`FileTree.test.tsx`, `SearchPanel.test.tsx`, `TerminalPanel.test.tsx`) that the new viewer skipped. Compounding this, the error state (`&lt;p className="binary-placeholder"&gt;{error}&lt;/p&gt;`) had no `role`/`aria-live`, so a screen-reader user who triggers an unparseable-file error gets no announcement. **Fix**: added `role="alert"` to the error paragraph in `PptxViewer.tsx`, and added two `jest-axe` assertions to `PptxViewer.test.tsx` — one for a normal rendered slide (with notes), one for the error state — both passing with zero violations.

**Findings acknowledged and deferred (non-blocking, tracked as follow-ups):**

3. **[Resource exhaustion, deferred]** `PptxViewer.tsx`'s `JSZip.loadAsync` and per-part `.async(...)` calls have no size/entry-count cap, so a crafted `.pptx` with highly compressible entries (a zip bomb) could freeze or OOM the browser tab. This mirrors the same absence of caps in the existing PDF/CSV/Excel viewers, is read-only and client-side (single-tab blast radius), and requires the user to actively open the malicious file in this single-user local desktop tool. Not blocking; worth a follow-up if this pattern is revisited across all lazily-loaded viewers at once.
4. **[TOCTOU, deferred]** `resolveSafeRepoPath`'s containment re-check happens once, up front; the subsequent `mkdir`/`writeFile`/`unlink` syscalls use the previously-resolved path string rather than a re-resolved handle. A symlink swapped into place between the check and the syscall could still escape. This is an inherent limitation of path-based (non-fd/`O_NOFOLLOW`-based) containment checks; low severity for a single-user local tool, and not a regression (the pre-existing code had the same structural limitation, now with a stronger per-segment check ahead of it).
5. **[Unbounded memory, deferred]** `PptxViewer.tsx` decodes and holds every slide's embedded images as full data URIs in state up front, rather than lazily per-visible-slide. Matches the already-shipped `ExcelViewer` pattern of loading the whole file into memory; not a regression, but worth a follow-up if a future spec targets streaming/lazy loading across viewers.
6. **[Pre-existing accessibility gaps, deferred, unchanged from sibling viewers]**: the loading skeleton (`aria-label="loading presentation"`) isn't a live region, and the nav buttons have no dedicated `:focus-visible` style — both match `PdfViewer.tsx`/`ExcelViewer.tsx`'s existing patterns exactly, so neither is a regression introduced by this branch.

**No other issues found.** All three agents' full reports were reviewed. The bugs/security agent specifically tried to break: multi-hop/chained/cyclic symlink escapes, colon-in-filename search parsing with multiple colons, PPTX XSS via `<img>` data-URI mime sniffing, PPTX path traversal via `../` in relationship targets, and prototype pollution via `fast-xml-parser` output — none succeeded. The performance agent verified the claimed per-slide event-loop yield is genuinely implemented (not just asserted in a comment), and confirmed `jszip`/`fast-xml-parser` stay lazy-loaded and out of the main bundle. `npx knip` findings are all pre-existing baseline noise unrelated to this branch.

## Addendum: startup-fallback fix (not part of spec 039)

### Summary

Fixed a long-standing "empty folder view on launch" problem, reported directly by the user as one of GitLocal's oldest known issues. Root cause: `initializePaths` (`src/server.ts`) committed to whatever repo path it was given without ever checking it still existed or was readable — an existing test had even locked this in as intentional behavior. A deleted/renamed/no-longer-readable "last used" or explicit-launch folder therefore silently rendered as a normal, empty, non-git folder with no explanation, and the only way out was the user manually navigating to a parent folder and back (which itself could land on another broken directory).

Changes:
- New `resolveGuaranteedFallbackPath()` (`src/services/startup-preferences.ts`): a cross-platform chain — Documents → home → `process.cwd()` → OS temp dir → filesystem/drive root — returning the first directory verified readable right now.
- `initializePaths` now checks existence, type, and readability before committing to a repo path; on failure it falls into picker mode pointed at the guaranteed fallback, with a clear explanatory message surfaced through the existing `/api/startup-folder` → picker-banner mechanism (new `StartupFolderSource` value `'safe-fallback'`).
- New self-healing check at the top of `infoHandler`: re-verifies the currently-open folder on every `/api/info` request, recovering automatically if it vanished mid-session (external drive unplugged, folder deleted while GitLocal was already open).
- `repositoryParentFolderHandler` now walks up past any unreadable ancestor instead of committing to a broken immediate parent.

### Contrarian QA (this addendum)

A dedicated contrarian-QA pass reviewed this addendum specifically (in addition to the three-agent pass on the rest of the branch, above), assuming regressions exist rather than presuming readiness. Two real findings, both fixed:

1. **[Dropped explanation on a doubly-rare fallback path, fixed]** When `repositoryParentFolderHandler`'s ancestor walk failed to find any readable directory all the way to the filesystem root, it returned an ad hoc `warning` field that no client ever reads (`LocalActionResponse` has no such field, and `App.tsx`'s success handler reloads the page immediately without inspecting the response body) — so the one case this whole feature exists to fix would have silently lost its own explanation. **Fix**: that branch now calls the same `setStartupFolderResolution` every other fallback path uses, so the reloaded picker page's existing banner mechanism picks up the message correctly. This path requires every ancestor up to the filesystem root to be unreadable, so it remains `/* v8 ignore */`d as impractical to exercise in a test.
2. **[Self-heal on a single transient read failure could regress a healthy session, fixed]** The mid-session self-heal treated any single failed readability check as permanent, with no allowance for a momentary hiccup (e.g. a network-mounted drive stalling rather than cleanly disconnecting) — indistinguishable from genuine, sustained unavailability, this could in principle kick a perfectly healthy, currently-open repo into picker mode on a one-off blip. **Fix**: a path that no longer exists at all (unambiguous) still heals immediately, matching the primary bug scenario unchanged; a path that still exists but fails only the readability check now requires two consecutive failed checks (naturally spaced by real request intervals — the next window refocus or manual Refresh) before recovering, with the streak keyed to the specific path and reset on success. Verified via two new tests: one asserting the first blip still surfaces as the pre-existing 500 (not yet a fake empty view), the second consecutive check recovering; another confirming the streak resets once the folder becomes readable again.

No other issues found. The agent additionally traced the ordinary (existing, readable folder) path through `initializePaths` and confirmed it takes the same early-return branches as before with only one added stat+readdir check — no behavior change for the common case — and verified the parent-walk loop terminates correctly at the filesystem root on both POSIX and Windows-style paths.

### Verification

- `npm test`: server 460/460, UI 517/517, all passing; no per-file coverage-gate failures.
- `npm run lint` (`tsc --noEmit`): clean.
- `npm run build`: server and UI bundles build cleanly.
- Manual end-to-end verification against the built server (`node dist/cli.js`) for three real scenarios: (1) a CLI argument pointing at a nonexistent folder — now falls back to a readable folder with an explanatory `fallbackReason` instead of silently opening the missing path; (2) a stale remembered "last used" folder pointing at a deleted directory (no CLI argument, matching normal launch) — already correctly fell back via the pre-existing `resolveStartupFolder` chain; (3) confirmed via the new automated tests that an unreadable directory passed directly to `createApp`, a mid-session permission change, and an unreadable parent during "go up a folder" all now recover with a clear message rather than silently rendering empty.

### Residual Risk (addendum)

- Both contrarian-QA findings were fixed and re-verified.
- The two-consecutive-failure debounce for the "exists but unreadable" case means a genuinely permanent permission change or drive disconnect takes one extra `/api/info` request to recover from (typically the next window refocus) rather than the very first one — an intentional, disclosed tradeoff to avoid over-reacting to a single transient glitch, not a regression of the primary bug being fixed (a confirmed-deleted/renamed path still heals immediately, with no debounce).

## Addendum 2: deep-dive code review follow-up fixes (not part of spec 039)

A separate, deeper code review of the entire app startup flow (`src/server.ts`, `src/cli.ts`, `src/services/startup-preferences.ts`, `src/handlers/repo.ts`, `src/git/repo.ts`, `ui/src/App.tsx`, `ui/src/components/Picker/PickerPage.tsx`, `native/macos`) surfaced 7 findings against the addendum-1 work above. All 7 were fixed; working notes for each are in `STARTUP-FLOW-FIXES.md` (deleted once this addendum was written, since its job — surviving a restart mid-fix — was done). Summary:

1. **Duplicated fallback-resolution object (simplification)**: the same `StartupFolderResolution` shape was built inline at 4 call sites across `src/server.ts` and `src/handlers/repo.ts`. Factored into one shared `buildSafeFallbackResolution` helper in `src/services/startup-preferences.ts`.
2. **Dead `message` field (correctness)**: `infoHandler`'s self-heal response attached a `message` field that `RepoInfo` doesn't declare and no frontend code reads. Removed; the explanation already reaches the user correctly via the `/api/startup-folder` → picker-banner channel every other fallback path uses.
3. **Refresh didn't refetch the startup-folder banner (correctness)**: `WORKSPACE_QUERY_KEYS` (invalidated by the manual Refresh button) didn't include `'startup-folder'`. Fixing this by adding it to the shared array broke an unrelated existing test (`applies startup-open target before saved viewer state...`) via a fragile batching/ordering interaction with the open-target-acceptance flow that shares that array — root cause not fully identified despite investigation. Fixed instead by invalidating `'startup-folder'` directly inside `refreshCurrentView` alone, achieving the same user-facing result without touching the shared array. Flagged as a follow-up investigation, not blocking.
4. **Parent-folder walk had no transient-failure protection (correctness)**: unlike the mid-session self-heal's two-consecutive-failure debounce, a single failed readability check during "go up a folder" was treated as permanent. Added an immediate same-request double-check (`isConfirmedUnreadable`) — the practical equivalent for a handler that only gets one shot per click, with an honestly-documented limitation (doesn't protect against a stall longer than the gap between the two checks).
5. **Leftover quoting-unsafe git status parsing (correctness, pre-existing, separate bug)**: `getWorkingTreeChanges` (feeds `getWorkingTreeRevision`'s cache-key hash) still used the old newline/`' -> '`-splitting parser spec 039 (US3) had already fixed in a sibling function. Fully deduplicated: `getWorkingTreeChanges` now reuses `getWorkingTreeChangeDetails`'s NUL-delimited parser instead of running its own separate, unsafe one.
6. **`/api/info` reads the repo root directory on every healthy request (efficiency)**: added a cheaper `isAccessibleDirectory` (permission-bit check via `accessSync`, no directory listing) for this specific hot path, leaving the stronger `readdirSync`-based `isReadableDirectory` in place everywhere else (the guaranteed-fallback chain, the parent-folder walk) where it runs far less often and the stronger guarantee is worth the cost.
7. **Changed-files review does O(changed files) extra syscalls per request (efficiency)**: the per-segment symlink-escape re-check added for the write-path containment fix (spec 039 US1) was also running on every changed file's read-only classification via `getPathType`. Added a cheaper `resolveClassificationPath` that keeps the lexical `../`-escape guard but skips the expensive re-check — safe because every actual write independently re-resolves and re-checks containment right before mutating, regardless of what any earlier `getPathType` call returned.

**Verification**: full suite (`npm test`: server 463/463, UI 518/518), `npm run lint`, and `npm run build` all pass after every fix, not just at the end. New/extended tests added for findings 3, 4, 5, and 7; findings 1, 2, and 6 were verified via the existing suite plus manual reasoning about call-site behavior (1 and 2 are internal refactors with no behavior change; 6 is a pure performance change with existing tests covering the same code paths).

**Residual risk**: finding 3's root cause (the `WORKSPACE_QUERY_KEYS` batching interaction) was not fully identified — noted as a follow-up investigation rather than blocking, since the shipped fix achieves the correct user-facing behavior via a narrower, verified-safe path.
- CLI positional-argument launches with a bad path fall back to a readable folder correctly but are a secondary path through `initializePaths` (the `options.initialOpenSource` branch) — verified manually end-to-end rather than via a new automated test, since the existing test suite for this branch is integration-level and the scenario was already covered qualitatively by the broader `initializePaths` test changes.
